# Tech choices

The technologies and frameworks the project uses, and why. Each entry has a short description,
then pros, cons, the reason we picked it, and what we could have used instead.

## Contract and API

### Protobuf + buf

A language-neutral way to define messages and services. A generator then writes the code for each
language. You only describe the data and the methods.
- All 13 `.proto` files in `proto/music_room/v1/` share one package, `music_room.v1`. They define
  6 services: Auth, User, MusicProvider, Playlist, Event, Delegation.
- `buf` lints the files, checks for breaking changes against `main`, and runs the generators. One run
  writes the Go structs, gRPC stubs and REST gateway for the backend, the Dart stubs for the app,
  and the Swagger spec.

| | |
| --- | --- |
| **Pros** | Typed interfaces on both sides from one file. You can add fields without breaking old clients, because fields are identified by number. It works with any language or platform. |
| **Cons** | The binary format is not human-readable. It needs a codegen toolchain, and the generated folders are gitignored, so a fresh clone or a proto change needs `make generate` first. |
| **Why we chose it** | It is the natural fit for gRPC. One edit to a proto file updates the server, the app and the API docs, which saves a lot of hand-written code. |
| **Alternatives** | OpenAPI/JSON Schema written by hand, GraphQL schemas, or hand-written JSON models on each side. |

### gRPC

RPC = Remote Procedure Call. The client calls a server method as if it were a local function.
gRPC sends protobuf messages over HTTP/2.
- The app uses unary calls for normal requests and server streams for live updates
  (`WatchPlaylist`, `WatchEvent`).

| | |
| --- | --- |
| **Pros** | Fast and compact. Generated, typed clients in Go and Dart. Streaming is built in. Reflection lets `grpcurl` call the server without stubs. |
| **Cons** | Browsers can't call it directly, so a REST gateway is needed. It's harder to inspect than JSON (you need `grpcurl`). The default 4 MiB message limit had to be raised for avatar uploads. |
| **Why we chose it** | One contract gives both the Go server and the Dart client, and server streams give us realtime updates without a separate WebSocket protocol. The REST and Swagger the subject asks for come from grpc-gateway, so we don't lose them.<br>Note: the backend talks to OpenFGA over **HTTP**, not gRPC (Go SDK). Switching is listed as possible future work in `docs/annex/load-testing.md`. |
| **Alternatives** | REST/JSON with a WebSocket for live data, GraphQL with subscriptions, Connect RPC. |

### grpc-gateway + Swagger

A generated reverse proxy that turns REST/JSON calls into gRPC calls. The REST routes are declared
as annotations in the proto files.
- It runs in the same Go process on `:8081` and dials the gRPC port over loopback, so REST hits
  the same handlers and the same permission checks.
- Swagger UI is served by the backend at `/docs/`, from the spec generated by buf.
- Used by the pytest suite and the k6 load tests or eventual web clients. The app itself uses gRPC.

| | |
| --- | --- |
| **Pros** | REST and API docs for free, nothing implemented twice. |
| **Cons** | One more generated layer. It only forwards some HTTP headers (custom ones need the `Grpc-Metadata-` prefix or a custom matcher). JSON field naming and defaults differ slightly from protobuf. |
| **Why we chose it** | The subject prefers REST with generated docs. This meets it without giving up gRPC. |
| **Alternatives** | A hand-written REST layer, Connect RPC (serves gRPC and JSON on one port), Envoy's gRPC-JSON transcoder. |

## Backend

### Go

The backend language. One binary serves gRPC, REST, Swagger, images and the OAuth callback.

| | |
| --- | --- |
| **Pros** | Simple language, fast compile, one static binary (the image is distroless). Goroutines make streams and background workers cheap. First-class gRPC support. |
| **Cons** | Verbose error handling, fewer high-level libraries than Java or Node. No exceptions or generics-heavy patterns, so some code is repetitive. |
| **Why we chose it** | Good fit for a gRPC server with many concurrent streams, and easy to read for the whole team (C/C++ background common to all 4 members). |
| **Alternatives** | Node.js/TypeScript, Java/Kotlin with Spring, Rust, Python (FastAPI). |

### PostgreSQL 16 + pgx

The main database, accessed through the `pgx` driver and its connection pool.
- We use many Postgres-specific features: `citext` emails, native enums, `jsonb`, `NUMERIC`
  positions, partial unique indexes, monthly partitions for `activity_logs`, row locks and
  `FOR UPDATE SKIP LOCKED` for the outbox.

| | |
| --- | --- |
| **Pros** | Strong transactions and constraints, so many rules are enforced by the database itself. Mature and well-known. Team member familiarity. |
| **Cons** | One more service to run. Some rules can't be in SQL (`NOW()` is not allowed in a `CHECK`), so they live in Go. |
| **Why we chose it** | The three services need concurrent writes that stay correct (votes, playlist edits). Postgres gives that with plain `READ COMMITTED` and row locks. |
| **Alternatives** | MySQL/MariaDB, SQLite, MongoDB. |

### sqlc

A tool that turns hand-written SQL into Go code.
- You write the schema and the queries in SQL (`backend/db/query/*.sql`).
- sqlc generates Go structs for the tables and one typed Go method per query.

| | |
| --- | --- |
| **Pros** | Full control of every query, and the Go code is still type-safe. Queries are checked against the schema at generation time. |
| **Cons** | You have to write SQL, which is a different skill from object-oriented code. The generated code is gitignored and must be regenerated. Some types need overrides (`citext`, `inet`), and the partitions are hidden in a `DO` block so sqlc doesn't create 25 fake models. |
| **Why we chose it** | Some features have concurrency problems (votes, playlist revisions) that need exact SQL: row locks, a fixed order of statements, `SKIP LOCKED`. An ORM hides those queries. Transactions themselves are opened in Go (`pool.Begin`). |
| **Alternatives** | An ORM (GORM, ent), raw `pgx` with hand-written scanning, sqlx, Jet. |

### goose

A migration tool. Each schema change is a numbered SQL file in `backend/db/schema/`.
- The files are embedded in the binary at compile time (`//go:embed`) and applied when the backend
  starts (`goose.Up` in `main.go`).
- All 23 migrations are SQL. goose also supports Go migrations, but we don't use them.

| | |
| --- | --- |
| **Pros** | Plain SQL files, no separate migration step to remember. A fresh database is ready as soon as the backend boots. |
| **Cons** | • The folder must stay flat: files in subfolders are silently ignored.<br>• Writing a `+goose` annotation inside a comment breaks the file.<br>• Editing an old migration does nothing on existing databases. |
| **Why we chose it** | Simple, SQL-first, and works with `go:embed`, so the binary carries its own schema. |
| **Alternatives** | Golang-migrate, Atlas, tern. |

### OpenFGA

A ReBAC (Relationship-Based Access Control) permission server.
- The model (`authz/model.fga`) defines types (user, playlist, event, queue entry, device, image)
  and how permissions follow from relationships, for example
  `can_edit_songs: owner or admin or editor or (can_view and open_edit)`.
- We write tuples ("user X is editor of playlist Y") derived from our Postgres rows. OpenFGA walks
  the graph to answer a `Check` ("can X edit Y?") or a `ListObjects` ("which playlists can X see?").
- Every RPC is checked in the interceptor. Tuples are kept in sync through a transactional outbox.

| | |
| --- | --- |
| **Pros** | The permission rules are in one readable file. A change cascades automatically (remove a friend, and every right that came from the friendship goes too). It replaces scattered Go/SQL checks. |
| **Cons** | • It was the **first bottleneck** under load (CPU-bound).<br>• The check cache makes a `Check` 1–2 s stale after a revocation.<br>• It needs its own Postgres.<br>• Keeping it in sync with our database needs an outbox and a worker.<br>• Google's Common Expression Language (CEL) conditions can't do geography, so the venue radius check stays in Go. |
| **Why we chose it** | Perfect for a collaborative app, where access comes from ownership, membership, friendship and licences rather than fixed roles. |
| **Alternatives** | Checks in Go/SQL, SpiceDB, Casbin, OPA, Permify. |

### Opaque session tokens (not JWT)

Login returns a random 32-byte token. The server stores only its SHA-256 hash in `user_sessions`
and looks it up on every request.

| | |
| --- | --- |
| **Pros** | Logout and revocation take effect on the next request. No refresh tokens, no rotation, no signing keys. |
| **Cons** | One database read per authenticated request. |
| **Why we chose it** | A signed JWT can't be revoked before it expires, and the access/refresh split only exists to work around that. One indexed read is cheap at our scale. |
| **Alternatives** | JWT access + refresh tokens, PASETO. |

### Argon2id

Password hashing (`golang.org/x/crypto/argon2`, 64 MiB memory, PHC string format).

| | |
| --- | --- |
| **Pros** | Current best practice, resistant to GPU cracking. |
| **Cons** | Each login costs 64 MiB of memory and real CPU, which matters in load tests. |
| **Why we chose it** | Recommended by OWASP for new projects. |
| **Alternatives** | Bcrypt, scrypt, PBKDF2. |

### OAuth (Google, 42)

Social login, written by hand against each provider's token and user-info URLs. The provider
redirects to the backend's `/oauth/callback`, which sends the code back to the app
(`musicroom://oauth`).

| | |
| --- | --- |
| **Pros** | No extra library, and each provider's quirks are in one small file. Providers without a client ID are simply turned off. |
| **Cons** | Each provider must be registered by hand. No PKCE yet. |
| **Why we chose it** | The subject asks for social sign-in. Both providers have similar flows. A Facebook provider is written too, but no Meta developer app could be registered, so the app does not show it. |
| **Alternatives** | `golang.org/x/oauth2`, an identity service (Keycloak, Auth0, Firebase Auth). |

### Realtime: in-memory hub + gRPC streams

After each write, a service sends an empty signal on a topic (`playlist:<id>`, `event:<id>`). Every
open `Watch` stream on that topic re-reads the full state and pushes it to its phone.

| | |
| --- | --- |
| **Pros** | The signal carries no data, so it can't be stale. A burst of writes becomes one re-read. No extra protocol: it's the same gRPC connection. |
| **Cons** | The hub lives in memory, so it only works with one backend process. Streams re-check permissions every 5 s rather than instantly. |
| **Why we chose it** | Simplest thing that works for one server. |
| **Alternatives** | WebSockets, Server-Sent Events, Redis pub/sub or Postgres `LISTEN/NOTIFY` for several backend processes. |

### Rate limiting (in memory)

Token buckets from `golang.org/x/time/rate`: per IP on every call, and per user on the social routes.
Logins have their own limit, counted in Postgres.

| | |
| --- | --- |
| **Pros** | No dependency, very cheap. |
| **Cons** | Counters are per process and reset on restart. The load test has to turn it off, since k6 sends everything from one IP. |
| **Why we chose it** | There is only one backend, so a shared counter isn't needed yet. |
| **Alternatives** | Redis counters, a limit at a reverse proxy (nginx, Envoy). |

### Redis

An in-memory key-value store. It runs in Docker Compose, but **the backend no longer connects to
it** and nothing is stored in it.

| | |
| --- | --- |
| **Pros** | Would be the natural place for a session cache, cross-process pub/sub, or shared rate limits. |
| **Cons** | One more service with nothing to do today. |
| **Why we chose it** | Kept for later. `docs/annex/data-model.md` §5 lists what would move to Redis, in order, and says the trigger is a measurement, not a preference. |
| **Alternatives** | Postgres alone (what we do now), Valkey, Memcached. |

### Deezer API

The song catalogue. Search goes to Deezer's public API, and a track is copied into our `songs` table
the first time a playlist or queue uses it.

| | |
| --- | --- |
| **Pros** | Free, no API key, and it gives 30-second preview links the app can play. |
| **Cons** | Only 30-second previews, preview links expire after 15 minutes, and errors come back as HTTP 200 and must be checked by hand. |
| **Why we chose it** | Playable audio with no account, no key and no review process. |
| **Alternatives** | Spotify (needs OAuth and Premium for playback), Apple Music, Jamendo, SoundCloud. |

### Image service (Rust, axum)

A small stateless service that resizes avatars and covers (`POST /resize`). The backend stores the
files itself and serves them at `/media/`.

| | |
| --- | --- |
| **Pros** | Tiny, fast, isolated: a bad image can't take the main backend down. |
| **Cons** | A second language and a second service. The size limit must agree in three places. |
| **Why we chose it** | Image decoding is CPU-heavy and self-contained, a good job for a small, separate Rust service. |
| **Alternatives** | Resize in Go (`image` package, `disintegration/imaging`), libvips, an image CDN. |

## Frontend

### Flutter / Dart

A UI framework. Dart is compiled to native code, and Flutter draws its own UI, so one codebase runs
on mobile and desktop.
- The builds we use: Android (APK), Linux (the eval "phone"), and macOS/iOS during development.
  The web build is not used.

| | |
| --- | --- |
| **Pros** | One codebase for every platform, hot reload, the same look everywhere. |
| **Cons** | Dart is a less common language. Native features (keychain, audio, webview) need plugins, and some have gaps on Linux. |
| **Why we chose it** | One app for Android and iOS, plus a desktop build that runs on eval machines without an emulator. |
| **Alternatives** | React Native, Kotlin Multiplatform, native Swift + Kotlin. |

### grpc-dart

The Dart gRPC client, with stubs generated from the same protos as the backend.
- `AuthInterceptor` adds `authorization: Bearer` to every call. `LiveStream` keeps the `Watch`
  streams open and reconnects them.

| | |
| --- | --- |
| **Pros** | Typed calls with no hand-written JSON models. The same streaming as the server. |
| **Cons** | Interceptors belong to each generated client, not to the channel, so every client has to be built with them. |
| **Why we chose it** | It follows from choosing gRPC. |
| **Alternatives** | REST through the generated OpenAPI client (exists, but unused), grpc-web. |

### provider + ValueNotifier stores

`provider` hands shared objects (network, stores, API interfaces) down the widget tree. Each feature
store holds its state in `ValueNotifier`s that widgets listen to.

| | |
| --- | --- |
| **Pros** | Small, built on Flutter's own primitives, easy to test with fake APIs. |
| **Cons** | More manual wiring than bigger frameworks. Disposing streams is the store's job. |
| **Why we chose it** | Simple and well documented, and enough for the app's size. |
| **Alternatives** | Riverpod, Bloc, GetX, MobX. |

### go_router

Declarative routing. `authRedirect` sends a signed-out user to `/login` and an unverified one to
`/verify-email`, and reruns whenever the session changes.

| | |
| --- | --- |
| **Pros** | Routes in one place, redirects as a plain function that is easy to test. |
| **Cons** | The router must be built once: rebuilding it resets the navigation stack. |
| **Why we chose it** | The routing package maintained by the Flutter team. |
| **Alternatives** | Navigator 2.0 by hand, auto_route, beamer. |

### flutter_secure_storage

Stores the session token, the signed-in user and the install's device id in the OS keychain
(Keychain on iOS/macOS, Keystore on Android, libsecret on Linux).

| | |
| --- | --- |
| **Pros** | The token never sits in plain files. |
| **Cons** | Different behaviour on each platform. On Linux it needs an unlocked keyring, which the phone container has to set up. |
| **Why we chose it** | The standard Flutter plugin for secrets. |
| **Alternatives** | Shared_preferences (not encrypted), Hive with encryption. |

### flutter_web_auth_2 (+ patched webview)

Opens the provider's login page and catches the redirect back to the app.
- On Linux the login window is the app's own webview, from a patched copy of
  `desktop_webview_window` in `frontend/app/third_party/` (the upstream version crashed on close).

| | |
| --- | --- |
| **Pros** | One OAuth flow for every platform. |
| **Cons** | We maintain a patched plugin. |
| **Why we chose it** | The most complete Flutter OAuth plugin, including desktop. |
| **Alternatives** | Flutter_appauth (no desktop), a hand-made webview flow. |

### just_audio + media_kit

Plays the 30-second Deezer previews, both for playlists and for event playback.
- just_audio has no Linux backend, so `just_audio_media_kit` (libmpv) fills that gap.

| | |
| --- | --- |
| **Pros** | One audio API on every platform. |
| **Cons** | An extra native library on Linux, and some states (end of track) behave differently there. |
| **Why we chose it** | The most used Flutter audio player. |
| **Alternatives** | Audioplayers, media_kit alone. |

### flutter_map + OpenStreetMap + geolocator

The venue map and the phone's position, used for events where only people at the venue can vote.

| | |
| --- | --- |
| **Pros** | Free tiles with no API key. On the Linux phone, the position comes from a file the browser page sets. |
| **Cons** | Tiles need the internet. OSM's tile policy requires a real user-agent. |
| **Why we chose it** | No key and no billing account. |
| **Alternatives** | Google_maps_flutter, Mapbox. |

## Running and testing

### Docker + Compose + Makefile

Everything runs in containers, started through the root `Makefile` (`make eval`, `make all`, …).
- The stack: Postgres, Redis, OpenFGA with its own Postgres, the backend, the image service, and
  optional phone and Android profiles.
- Multi-stage Dockerfiles build the code inside the images, including codegen.

| | |
| --- | --- |
| **Pros** | The eval machines only need Docker and `make`. One command starts everything. |
| **Cons** | Large images and long first builds. Low-disk machines need special targets. |
| **Why we chose it** | The eval machines have Docker and nothing else. |
| **Alternatives** | Installing the tools on the host, Nix, Kubernetes (too much for this). |

### The "phone" (Linux build in the browser)

The Flutter Linux build runs in a container on Xvfb and is shown in the browser through noVNC
(`:6080`). Sound and position are bridged to the page too.

| | |
| --- | --- |
| **Pros** | Works on machines with no `/dev/kvm`. Uses the same native gRPC path as Android. |
| **Cons** | It's not a real phone: software rendering, a keyring to unlock, no real GPS. |
| **Why we chose it** | An Android emulator can't boot without `/dev/kvm`. `make apk` still gives an APK for a real phone, and `make android` runs an emulator where KVM exists. |
| **Alternatives** | An Android emulator (needs KVM), a real phone over the LAN, the web build. |

### k6 (load testing)

A load-testing tool where scenarios are written in JavaScript (`loadtest/`).
- It runs in its own compose project with CPU limits on each server container. It ramps from 25 to
  800 virtual users (or more) through the REST gateway.
- Results on a dev Mac: about 1000 simultaneous users before breaking at 1200. OpenFGA was the
  first bottleneck. `docs/annex/load-testing.md` has the details.

| | |
| --- | --- |
| **Pros** | Scenarios are plain code, clear pass/fail thresholds, live dashboard, one Docker image. |
| **Cons** | It tests REST, not the app's gRPC path (a conservative bound). |
| **Why we chose it** | Easy to script, light on resources, and it runs in Docker. |
| **Alternatives** | Locust, JMeter, Gatling, vegeta. |

### pytest + grpcurl (API tests)

A black-box test suite in Python (`tests/`, 218 tests) that runs against the live stack.
- Most tests use REST. The auth tests call gRPC through `grpcurl`. Fixtures write users and sessions
  directly in Postgres.

| | |
| --- | --- |
| **Pros** | Tests what a real client sees, including the gateway's JSON. Quick to write. |
| **Cons** | Needs the whole stack running. Writing to the database directly ties the tests to the schema. |
| **Why we chose it** | Python is fast for test code, and `grpcurl` avoids generating Python stubs. |
| **Alternatives** | Go integration tests (there are some), Postman/Newman, Bruno. |

### Seed (Go)

`backend/cmd/seed` fills the database with a demo world (122 accounts) or with load-test users.
It is built into the backend image.

| | |
| --- | --- |
| **Pros** | Same language and queries as the backend, so it stays correct when the schema changes. Its doc (`docs/annex/init_script_doc.md`) is generated, and a test fails if they disagree. |
| **Cons** | Large seeds are slow while the backend runs (the outbox has to catch up). |
| **Why we chose it** | Reuses the sqlc queries instead of duplicating the schema in a script. |
| **Alternatives** | SQL fixture files, a Python script. |
